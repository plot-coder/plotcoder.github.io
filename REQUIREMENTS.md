# PlotCoder Requirements

Living product requirements for PlotCoder. This file is the source of truth for what we are building and why. Update it whenever Robert states a new requirement, changes a decision, or we notice two tools should be combined or cut.

Other agents: read this file before reviewing or adding code. Treat **Confirmed** items as constraints. Treat **Proposed** and **Open** items as discussion, not commitments. Prefer challenging the design against these requirements over inventing new scope.

---

## How we use this file

1. Robert states a need while we build.
2. We add it here as a numbered requirement with date, status, and the reason.
3. Periodically we review the list and ask: should two tools be one? Is this requirement still true? Is there a simpler way?
4. Other agents review against this document and write their perspective in [Reviewer notes](#reviewer-notes-other-agents).
5. **Anything a person will see is mocked before it is built** — on the app's own paper, beside what ships today — and the mockup is followed by one honest question, *is this the best we could do?*, answered in writing before a line of interface is written. Robert's standing instruction, 2026-09-13. Tools and plumbing skip the mockup, not the question.

## Product

**Name:** PlotCoder  
**Domain:** [plotcoder.com](https://plotcoder.com)  
**Kind of app:** Storylining app — a digital corkboard for breaking and rearranging plot before writing the script, growing into the full set of tools a screenwriter needs.

PlotCoder is for screenwriters who work the way rooms work: one card, one change, then rearrange the wall until the spine works. It is the board you use to string plot together, and then a set of tools around that board.

**Purpose, as stated by Robert on 2026-09-12 (D24, R26, R27):** PlotCoder is a set of tools for building a storyline, covering the activities a writer does today in Final Draft. It is designed so that an **agent driven by a person** has every one of those tools — the person directs, the agent operates, and the board on screen is the person's window onto the same records. The wall came first because it is the part of the job Final Draft does worst. Long term, once the tools exist, unique **workflows** are launched on top of them: sequences of tool calls a writer starts as one act. The furthest of those (D25, R28): once a person has made a storyline they believe in, the app helps them **drive agents that build segments of the movie** with video generation tools — Grok Video or whatever is best at the time. That is the horizon, not the plan; there is a great deal to build first.

**Said again by Robert on 2026-09-17, in one line:** *this app is designed to create stories from ideas and facilitate an agent helping a user do so.* Hold every decision against that sentence. It is why the blind runs continue: they measure the second half.

- Primary: screenwriters building features, TV episodes, and shorts.
- First user: Robert, using the real app as we invent it.
- Later: other writers, possibly more than one person on a board.

### R1 — Digital corkboard

- **Status:** confirmed
- **Date:** 2026-09-12
- **Statement:** The core tool is a board of movable cards used to string a plot together, in the spirit of Post-it / index-card storylining.
- **Why:** That is how Robert wants to work, and how professional rooms break story.
- **Notes:** A card should represent a scene or beat, not a slugline. Fields as built: headline, change, paper colour (R16), rank (R20), and length (R25). What else belongs on a card is open question 3.

### R2 — Tools, not one monolith on day one

- **Status:** confirmed
- **Date:** 2026-09-12
- **Statement:** PlotCoder will grow as a set of tools that help string plot together. We may later combine tools if this file shows they overlap.
- **Why:** Build by using it. Keep the option to merge or split as real use teaches us.
- **Reflection prompt:** Before adding a new tool, check whether an existing one already covers the job.

### R3 — Web first, PWA later

- **Status:** **built** 2026-09-13 (roadmap item 7; no mockup: platform)
- **Date:** 2026-09-12; built 2026-09-13
- **Statement:** The app runs as a normal website first, and is an installable progressive web app: a manifest, an icon, and a service worker that caches the built app so it opens offline and installs on a phone or a desktop.
- **Why:** Fast to use while we invent it; usable on a phone or offline like a real writers' tool.
- **As built:** `vite-plugin-pwa` in `vite.config.ts` writes the manifest and a Workbox service worker that precaches the whole built app (fourteen files) and updates quietly on the next open; off in dev, so the dev bridge and the end-to-end suite see plain Vite. The icon is a yellow card on black, `public/icon.svg`, rendered to the PNG sizes install needs. The service worker never touches the account or the bridge; localStorage was already the record when offline. **HTTPS:** GitHub Pages issued the certificate for `plotcoder.com` and `www.plotcoder.com` on 2026-09-13 once the custom domain was removed and re-added through the API (it had been stuck since v0.1.0), and Enforce HTTPS is on; the certificate renews itself.

### R4 — Supabase as the system of record

- **Status:** **built** 2026-09-13 (roadmap item 2; mocked two homes for the door, asked, revised, built)
- **Date:** 2026-09-12; built 2026-09-13
- **Statement:** Supabase is the system of record (Postgres, auth, later realtime). Sign in, and the same project is on every device. Signed out, the app is exactly as it was: `localStorage` is the cache, and the record when offline or signed out. No second custom backend.
- **Why:** Robert chose Supabase, and confirmed localStorage first so we could keep building without accounts. Item 2 wired it once the project model (R35) gave it a shape to hold.
- **As built:**
  - **The door is the transfer sheet** (mock option B, revised): Save, Open, and now Sign in live together because all three are "carry this project somewhere" (D10). Sign-in is a **magic link** by email, no password; Supabase's own mail sends it and the link opens back on the same origin. Signed in, the sheet says who and when — "Signed in as … · saved a moment ago" — and offers Sign out, which stops the mirror and leaves the wall on the device. Nobody is asked to sign in before they have a wall worth keeping; the sheet asks once, when they open it to save.
  - **The state is on the button** (from mock option A): the transfer button carries a dot — green when saved to the account, pulsing while saving, warm when offline with changes waiting. Signed out, no dot at all, which is honest: a file is the only carrier.
  - **The tables**, on the `beehealers` project (D27): `plotcoder_projects` (id, owner, `record` JSON — the R35 project record — `reminders` JSON, `rev`) and `plotcoder_boards` (id, project, owner, `state` JSON — a whole `BoardState` — `rev`). Row-level security by owner on both, for every verb, and nothing else. Boards are documents with a revision, exactly the shape the dev bridge speaks. Checked: the publishable key alone reads nothing and cannot write.
  - **The mirror** (`src/board/account.ts`) is a fourth mirror beside localStorage, the bridge and `window.plotcoder`. It pushes on change with the revision it last saw, pulls on sign-in and on open, and keeps per-row bookkeeping — last seen revision, unpushed changes — outside the `plotcoder.` prefix so a project file never carries it (R12). Reminders (R11) ride on the project row.
  - **The rules are pure** (`src/board/sync.js`, tested): what a device does on meeting the account (the account's project wins; boards only this device has are carried in, renamed for the device and time, unless the device holds nothing but the seed wall), what a push does when it finds the account ahead, and what opening does with a board that moved elsewhere. **Conflict:** the account's copy stays the board, and this device's copy becomes a **new board named "Episode 2 · from a Mac, 3:14 pm"**, said once in the sheet. Nothing is lost; there is no merge dialog; the writer merges by hand with the tools they have.
  - ~~**The agent door does not change.**~~ Since Roadmap 2 item 6 the MCP server has an account door beside the bridge and the file: the writer's own email and password in its environment, never a service key.
  - **Tests:** thirteen for the sync rules; the end-to-end suite stays offline, because the dev bridge is the test double the app already has. The deploy gains nothing secret: the URL and the publishable key ship in the app, as Supabase intends.
- **Notes (superseded 2026-09-13):** the magic-link door became the name on the door (R39); one project per writer became several (R40); two people on one board arrived (R41); and the data moved to PlotCoder's own Supabase project (D27 closed). The mirror, the bookkeeping and the conflict rule are as described above, with a project id in front of them.

- **Status:** confirmed
- **Date:** 2026-09-12

### R9 — Automatic theme at 8:00 a.m. and 8:00 p.m.

- **Status:** confirmed
- **Date:** 2026-09-12
- **Statement:** Every day, local time, the canvas becomes light at 8:00 a.m. and dark at 8:00 p.m. The general-bar switch can change the theme immediately. A manual choice lasts only until the next 8:00 a.m. or 8:00 p.m. boundary, then the clock takes over again.
- **Why:** The room should set itself for daytime writing and nighttime writing without a setting to babysit.

### R10 — Reminders modal

- **Status:** confirmed
- **Date:** 2026-09-12
- **Statement:** A **Reminders** button sits at the top right. Clicking it opens a modal of craft reminders. The first six are the story/character/structure/dialogue/camera/readability notes. The user can add more.
- **Why:** Keep the principles on the wall while writing, without putting them on the canvas.
- **Notes:** This is a dedicated control, not a general-bar item. Reminders are writing craft, not app settings.

### R11 — Reminder persistence

- **Status:** confirmed
- **Date:** 2026-09-12
- **Statement:** Added reminders must survive closing the tab. Store them in `localStorage` (`plotcoder.reminders`) now. When Supabase is added, move the same `{ id, title, body, builtIn, createdAt }` records into Postgres.
- **Why:** Robert confirmed localStorage now, Supabase later (D9).
- **Notes:** `localStorage` is per browser and per device. It does not sync phones and laptops.

### R12 — Save and open project

- **Status:** confirmed
- **Date:** 2026-09-12
- **Statement:** To the right of Reminders, an up-down arrow opens a modal. **Save project** downloads all `plotcoder.*` localStorage keys as a JSON file. **Open project** uploads that file and replaces the current localStorage project, then reloads.
- **Why:** localStorage does not sync. A file is how a user carries a project between computers until Supabase exists.
- **Notes:** The file is `{ app: "plotcoder", version: 1, exportedAt, storage }`. Only `plotcoder.*` keys are written. This is the same data we will later put in Supabase.

### R13 — Edit and move a note

- **Status:** confirmed
- **Date:** 2026-09-12
- **Statement:** Tap the **headline** or **change** line to type in place. Drag the **paper** (the empty margin or top strip) to move the card. First tap may select the card (outline). Tap the canvas or press Escape to stop editing.
- **Why:** The wall must both write and rearrange. Double-click fails on phones. Click-and-hold fights drag, which is the main gesture.
- **Notes:** Desktop may also double-click the card to focus the headline as a shortcut. Long-press may later open a menu (delete, more). Neither is required to edit. Color has its own control (R16).

### R14 — Group cards

- **Status:** **confirmed — mechanism locked** 2026-09-12 (P6 as built; answers open question 12)
- **Date:** 2026-09-12
- **Statement:** The user can group cards so a sequence, set piece, or cluster moves and reads as one unit. Cards stay visible; grouping is not a folder you open.
- **Why:** Rooms rubber-band a run of beats. Forty loose notes hide the sequences.
- **Proposed mechanism (P6):** Drag on empty canvas to lasso. With two or more selected, **Group** (general bar or a small selection chip) wraps them in a named frame. Drag the frame to move all. Drag a card out to leave. Edit the frame title (e.g. “Midpoint,” “Heist”). Do not auto-group by proximity.
- **Later, not now:** stacking one card on another (alternates for the same slot). That is a different meaning than a sequence frame.
- **Notes:** Groups are the same objects as cards, plus a parent. Do not invent a second “beat sheet” model.

### R15 — Arrows between cards

- **Status:** **confirmed — draw gesture locked** 2026-09-12 (P8 as built; answers open question 13)
- **Date:** 2026-09-12
- **Statement:** The user can draw an arrow from one card to another to show what comes after what. Arrows are **directed**. Drawing A→B does not create B→A. The user may also draw B→A, so two arrows can run opposite ways between the same pair. That is two objects, not one two-headed line.
- **Why:** Sequence is not only left-to-right position. Loops and mutual cause are real in story (“they keep triggering each other”).
- **Proposed draw (P8):** A small outbound handle on a card (visible when the card is selected or hovered). Drag from that handle onto another card to create A→B. Repeat the other way for B→A. Opposite arrows sit on **offset paths** so both heads stay readable. Click an arrow to select it; delete removes that direction only. Arrows stick to cards when cards move, organize, or group.
- **Drawn, 2026-09-13 (mocked before and after, at Robert's ask):** the big head stays at full size everywhere — Robert's call, twice. What changed is the path: **air** of up to 8px off the paper at both ends, so an arrow floats between cards instead of touching them; a **bow proportional to length**, capped at the old 28px, so a neighbour's arrow is a straight stitch and a long one curves as before; and between side-by-side neighbours the arrow **steps below the handle's row**, so the head and the handle stop sharing one gap. In a gap too tight for head plus air, the head keeps its size and the air is what is left, split evenly. The head is now a drawn shape rather than an SVG marker, so it can follow a curve's arrival angle and hold its size; same wedge, same 27×18. All in `src/arrowGeometry.ts`, tested.
- **Notes:** An arrow is not a group. Organize still uses reading order unless we later add “organize along arrows.” Do not auto-create the reverse. No unlabeled spaghetti: if we later need a label on an arrow, that is a new requirement. **2026-09-12:** it was, and it became a *kind* rather than a label — `follows` or `setup` (R30). Still no free text on an arrow. **Later that day:** the first floated-arrow build ended the shaft along the straight line between the cards while the head followed the curve, which at medium range left the head hanging off the shaft — Robert caught it. The shaft is now the curve itself, cut a head's length before the tip, and the head hangs off that point. Pinned by a medium-range test.

### R16 — Change a card’s paper color

- **Status:** **confirmed — gesture locked** 2026-09-12 (P10 as built; answers open question 14)
- **Date:** 2026-09-12
- **Statement:** The user can change a card’s paper color. Color is a property of the card, not a canvas setting. The five pad colors are yellow, pink, blue, green, and orange. They stay paper on both black and white canvases.
- **Why:** Rooms color a storyline, a character, or a tone. A random pad color is not enough once the wall is real work.
- **Proposed gesture (P10):** A small stacked-paper tab on the card (visible on hover or select, like the arrow handle). Click it to open the five swatches on that card. Click a swatch to set the color. If two or more cards are selected and you recolor one of them, the whole selection changes. Do not put color in the general bar. Do not require long-press or double-click.
- **Notes:** Meaning of a color (B-story, character, act) stays with the writer. We are not locking a legend yet.

### R17 — Agent command surface

- **Status:** **built** 2026-09-12 (P11 as built; mechanism locked)
- **Date:** 2026-09-12
- **Statement:** An agent or robot (including this assistant) can create cards and move things around without driving the mouse. The same operations a human does by hand — new note, move, recolor, edit, delete — are available as callable commands, and they land on the same board a human sees.
- **Why:** Robert wants to build the wall with an agent, not only by dragging paper. If the agent and the human edit through different code paths they will drift.
- **Proposed mechanism (P11):** One command kernel that both the human UI and the agent call. Three doors into it: the human gestures, a `window.plotcoder` API on the page, and an MCP server in the repo. A workspace board file lets commands work with the app closed.
- **As built:** fifty-five tools, covering every verb a person has — `list_board`, `read_wall` (R22), `undo` (R33), `organize` (R34); the project (`list_boards`, `open_board`, `new_board`, `rename_board`, `delete_board`, R35); the cast (`add_character`, `rename_character`, `remove_character`, `cast`, R29; `update_character`, R36); `set_location` (R37); `apply_template` (R38); the premise and reminders (`set_premise`, `rename_project`, `list_reminders`, `add_reminder`, `remove_reminder`, roadmap item 6); `export_fountain` (R23 slice a); `write_scene`, `read_pages`, `import_fountain` (R23 slice b); `list_workflows` (R27), `segment_brief` (R28); `page_count`, `export_fdx`, `import_fdx` (R23 slice c); `set_arrow_kind` (R30); `set_plant` (R31); cards (`create_note`, `update_note`, `move_note`, `recolor_note`, `set_rank`, `set_length`, `delete_note`); structure (`set_logline`, `set_target`, `create_group`, `rename_group`, `ungroup`, `create_arrow`, `delete_arrow`). Verified end to end by building a nine-card wall with beats, a named group and three arrows through the live bridge, with nothing faked.
- **Not exposed when built:** Organize and Scatter (UI-layer layout, not kernel commands), the series premise and Reminders (browser storage, not board data), and pan/zoom (per-viewer, D18). **R26 has since made the first four a backlog**, not a boundary; pan/zoom stays out on purpose.
- **Clients:** the server is wired for Cursor in `.cursor/mcp.json` and for Claude Code in `.mcp.json` at the repo root. One skill, `.cursor/skills/plotcoder-board/SKILL.md`, is shared by both: `.claude/skills/plotcoder-board` is a symlink to it, so there is one copy to keep true.
- **Refusals name their cause.** A tool that reports success on a rejected command teaches the agent the board is in a state it is not, so `create_arrow` distinguishes a self-link from an unknown id from a duplicate, and `create_group` names the ids that were not on the board. An agent that is told what is wrong fixes its input; an agent told "it failed" retries the same call.
- **Notes:** The agent must not fake pointer drags; it calls commands.

### R18 — The method the tools serve

- **Status:** proposed
- **Date:** 2026-09-12
- **Statement:** PlotCoder supports a specific order of work. (1) State the **logline / central question** — what the story is arguing. (2) Find the **beats** — 8 to 15 major turns (inciting incident, midpoint, lowest point, climax). (3) Fill the space between them with **scene cards**; one card is one scene. (4) **Read the wall** — look for a sagging Act 2, a missing setup, a character who disappears, two scenes that do the same job. (5) **Only then write pages** — or write one sequence, then restick the remaining cards.
- **Why:** Robert works this way. Recording the method makes it testable as a product: every feature below exists to serve one of the five steps, and a feature that serves none of them has to argue for itself.
- **Notes:** The order is a default, not a cage. Step 5 loops back to step 3 — that is the point of "restick the remaining cards." R19–R23 are the five steps as requirements.

### R19 — Logline / central question

- **Status:** **built** 2026-09-12
- **Date:** 2026-09-12

It stays visible while working rather than living inside a modal you have to remember to open. Above it, the project may hold a **series premise** shared by every board in it (D16, D17).

### R20 — Beats

- **Status:** **built** 2026-09-12
- **Date:** 2026-09-12
- **Statement:** Some cards are **beats**: the 8 to 15 major turns. A beat is a card with a different **rank**, not a different kind of object and not a second document.
- **Why:** Forty equal rectangles have no spine. The turns are what the rest hangs on.
- **As built:**
  - `rank` is `"scene"` or `"beat"` and lives on the card. Marking a beat **never moves it** (D20) — there is a test and a browser check pinning that, because the whole point of choosing the free wall is that meaning is not carried by position.

- **Migration:** cards written before R20 have no rank. `normalizeState` makes them **scenes**, because a beat is something you mark deliberately, so the default has to claim nothing. Second use of the pattern established by R19.

### R21 — Scene cards

- **Status:** **satisfied** 2026-09-12 — by R20, with no code of its own
- **Date:** 2026-09-12
- **Statement:** The rest of the cards are **scenes**. One card is one scene. Scenes fill the space between beats.
- **Why:** It is the unit the writer actually moves, and it keeps a card honest — if it needs two cards it is two scenes.
- **Resolution:** "One card is one scene" was already true — every card on the wall is a scene card, and now every card says so. ### R22 — Read the wall

- **Status:** **first slice built** 2026-09-12; the rest proposed
- **Date:** 2026-09-12
- **Statement:** The app helps the writer find what is wrong with the board: an act that sags, a setup with no payoff, a character who disappears for a stretch, two scenes doing the same job.
- **Why:** This is the step no other tool takes for the writer. Final Draft's reports count scenes and speeches for a production office; nobody answers "why does Act 2 feel long" at 2 a.m.
- **As built (first slice):** one pure kernel module, `src/board/readWall.js`, read through two doors — the **Reminders modal's second half** (P17: the principles above, the board read against them below) and a **`read_wall` MCP tool**. It returns a *reading* and a list of *questions*:
  - **The reading:** the cards in wall order, the beats, and the **runs** — the scene pages strictly between consecutive beats, plus the opening and closing runs. "About 12 pages between *Lock in* and *Midpoint*, 3 cards" is the sag detector R25 was built for, and it needs no act model.
  - **The questions**, each written as a question and never acted on: a run more than **twice the typical run** (sagging, or a set piece?); a card with a placeholder headline or **no change line**; once at least half the wall uses arrows, a card **no arrow touches**; two headlines that **read like the same scene**, measured on content words; a group **over twenty pages** (one sequence or two?). And, when nothing is marked, the fact that runs cannot be read until a beat is.
  - **Order:** the wall gives the order, and the wall is free (D20), so order is **reading order** — rows top to bottom, banded by half a card of drift, cards left to right within a row. **Arrows do not yet change the order.** That is the first refinement, once this slice has been used on a real wall.
  - **D21 holds:** it never says how many beats there should be. The MCP tool's description tells the agent the same.
- **Since then:** the cast (R29) added "a character who disappears" and "a person on no card". Typed arrows (R30) added the setups reading and "a payoff before its setup". The fold (R31) added "a setup with no payoff". **All four questions the statement names are now asked.** What is left is depth, not kind: the checks read only what the wall holds, and they ask, never fix.
- **Notes:** Raises questions, never auto-fixes. Lives in the Reminders modal, not a new panel.
- **A person's door (2026-09-13):** the **Asks** line in the bar's readout and the *What the wall asks* sheet — every finding under its kind, *show me* lighting the cards it is about, never dismissable (a question goes away when the wall answers it). The same reading `read_wall` gives an agent; nothing there moves a card.

### R23 — Pages come last

- **Status:** confirmed; **slices a, b and c built** 2026-09-13 (Fountain out; pages beside the wall; pagination and Final Draft)
- **Date:** 2026-09-12; slice a 2026-09-13
- **Statement:** Writing pages happens after the wall reads right. **PlotCoder will eventually be where it happens** (D22, 2026-09-12) — but not before the wall earns it.
- **Why:** The whole method is "earn the structure before you spend the pages." That is also the product order: a formatter built before the wall reads right would just be a worse Final Draft with none of the reason to switch.
- **Route:** **Fountain** first — a plain-text screenplay format that gets real, paginated pages for a fraction of the cost of `.fdx`. Then `.fdx` round-trip, which is the actual moat: studios, agencies and production offices expect Final Draft's file, and a tool that cannot hand one over does not get used on a paid job.
- **Known depth:** industry pagination is a standards problem, not a rendering problem — page-break rules, `(MORE)` and `(CONT'D)`, dual dialogue, scene numbering, revision marks. It is unglamorous and it is exactly where Final Draft's thirty-year lead lives. Do not start it early and do not underestimate it.
- **Notes:** Card length (R25) is the first step on this road: an estimate in the same unit real pages will later be measured in (D23).
- **Slice a, as built (2026-09-13):** `src/board/fountain.js`, pure and shared by every door, writes the open board as a Fountain document: a title page with the board's name (and "An episode of …" when the project has several boards), the draft date, and the premise, logline and the wall's numbers in its notes; beats as `#` sections; one scene per card in reading order — a forced heading from the card's place in capitals (or its headline when it has none), the headline as a `=` synopsis, the cast and the fold as a `[[note]]`, the change line as action. Everything but the heading and the action is invisible on a printed page, so the document reads as a script and outlines as the wall. Doors: **Save as Fountain** on the transfer sheet (a `.fountain` file named for the board), `window.plotcoder.fountain()`, and an `export_fountain` tool that returns the text or writes a file (thirty-eight tools). Mocked as text, not an interface, as the roadmap said.
- **Slice b, as built (2026-09-13; mocked three homes, asked, revised, built):**
  - **The text is on the card.** `text` on a card, empty by default (ninth board migration); `set_text` in the kernel, one undo step per scene. A card with text is **measured** — its lines against fifty-five to a page, in eighths — and one without keeps the estimate; `noteEighths` is the one reading of a card's length, used by the board total, read the wall, the Story Map, the person's page and `list_board` ("1/8pp written"). Fountain out writes the text as the scene's body when there is one and the change line when there is not.
  - **The panel (mock C, revised):** a **Pages** button beside Cast opens a panel down the right — the whole script in wall order, one scene per card: the heading from the place, the headline as a synopsis, the scene's text editable in Courier with the change line greyed as its placeholder, the measure beside each heading ("≈1 page · estimated" or "1 2/8 pages · measured"), beats as sections. Click a card and the panel scrolls to its scene; put the caret in a scene and its card lights and the wall pans to it. **Widen** takes the window and back; open and width are remembered per viewer. Escape leaves the scene, then closes the panel.
  - **The card and the strip:** the card's page count goes bold once measured; the Story Map hatches an estimated block and draws a measured one solid, so the axis says what it knows (D23: the unit does not change).
  - **Fountain in:** `fromFountain` parses a document (title page, sections, forced and standard headings, synopses, notes, boneyards) into scenes; `mergeFountain` writes each scene's text onto the card with the same heading in order, makes a card for a scene the wall lacks after the last matched one, and never deletes. A scene whose body is a card's own change line is the export of an unwritten card coming back and stays unwritten. Open project takes a `.fountain` file onto the open board and says what it did.
  - **Agent:** `write_scene`, `read_pages` (the script with each card's id and measure beside its heading), `import_fountain` (a path or text); forty-one tools. `window.plotcoder.writeScene`.
  - **Tests:** eight for the module and the measure, one MCP test, a tenth end-to-end spec for the new door.
  - **Mocked first:** pages as a mode replacing the wall (a continuous document, but the method's step 5 needs both in reach), the back of the card (charming, but a scene is not card-sized and there is no continuous read), and the panel beside the wall. The revision: the panel that widens, the card that lights, the axis that says what it knows, a merge that never deletes.
  - ~~**Not in this slice:** pagination, `(MORE)` and `(CONT'D)`, dual dialogue, scene numbers — slice c.~~ Built the same day; below.
- **Slice c, as built (2026-09-13; the standard drawn on a page, three homes mocked, asked, built in four pieces):**
  - **c1 · The paginator** (`src/board/paginate.js`, pure, ten tests against a sample with known breaks): a scene's Fountain becomes elements — action, character with parenthetical and dialogue, dual dialogue (`^`), transition, centred, page break — then lines at Courier 12 widths (heading and action 60, dialogue 35, parenthetical 25, a dual column 28), then pages of fifty-five lines with the rules: a heading keeps two lines of its scene with it or moves; a speech that does not fit splits **between sentences**, re-wrapped, with `(MORE)` under and `NAME (CONT'D)` over, or moves whole; action breaks between lines; dual dialogue sets side by side; scene numbers follow wall order. Nothing is stored: the card holds Fountain and every mark is computed. A written scene's measure now comes from the same line count, so the panel, the strip, read the wall and the printed page never disagree.
  - **c2 · The page in the panel** (mock A, revised): **As text · As pages** in the pages panel's head. As pages lays the script out as Letter pages on screen — the number top right, scene numbers in both margins, each element at its column, a dual pair in two columns — with the head saying "Pages · 14 of 120 · scene 14 on p. 12". Click a scene on the page and the panel returns to As text at that scene. **Print** opens the browser's print over a Letter stylesheet (an inch and a half left, an inch elsewhere, one page per sheet); **Save as PDF** on the transfer sheet does the same. The card's corner says **p. 12** once its scene has a page (C).
  - **c3 · Final Draft out** (`src/board/fdx.js`): one Paragraph per element, `DualDialogue` for a pair, `SceneProperties` and `Number` on each heading by wall order, the title page from the project with a line saying numbers are not locked. **Save as Final Draft** on the transfer sheet; `export_fdx` for agents.
  - **c4 · Final Draft in:** a small reader of exactly the tags Final Draft writes — styled `Text` runs joined, entities unescaped, `DualDialogue` flattened with the dual mark, numbers kept — into the same scenes Fountain in produces, then the same merge: by heading and order, never deleting. Open project takes a `.fdx`; `import_fdx` for agents; `page_count` gives an agent the page each scene starts on. **Round trip:** out then in changes nothing on the wall, and Final Draft in reads back exactly what Fountain in reads.
  - **The page as the editor (Roadmap 2, item 2, built 2026-09-13):** As pages is one continuous Letter-wide page on screen, and every scene on it is editable in place (`src/SceneEditor.tsx`): each of the writer's lines is one line, styled by what it is from the same rules the paginator reads by (`classifyLines`, pure, tested), at its column. Nothing computed is inside the text: the page turns are drawn beside the line the paginator says they fall on — a dashed rule with the new page's number, and `(MORE)` above and `NAME (CONT'D)` below when the turn falls inside a speech — and cannot be selected or deleted. Type and the turn moves. The store's copy lands only while the caret is elsewhere, as the card's lines do. Print sets the same script as separate pages.
  - **The receipt (Roadmap 2, item 3, built 2026-09-13):** Final Draft in now reads what a production draft carries that the wall does not hold — script notes, revision marks, locked scene numbers, forced page breaks, paragraph types read as action — and says so on the sheet and from the tool: "Kept out of the wall: … Nothing was deleted." A script note's text stays out of the paragraph it was pinned to.
  - **Honest limits:** the reader is still untested against a file Final Draft itself wrote — the receipt is built from the format's documented attributes; scene numbers are computed and not locked (question 23); no A/B pages or revision colours. Forty-six tools.

### R24 — The wall is bigger than the window

- **Status:** **built** 2026-09-12 (P18 as built)
- **Date:** 2026-09-12
- **Statement:** The board is an unbounded surface. The window shows part of it. The user can **pan** to reach any part of the wall and **zoom out** to see the whole thing at once. No card can ever become unreachable.
- **Why:** Measured on v0.1.0 with a feature-length board — 13 beats plus 40 scene cards, the scale R18's method actually implies — then pressed Organize on a 1440×900 laptop. **16 of the 53 cards were visible and the other 37 were unreachable.** Laid-out content ran 3,162px tall against a 900px viewport, the lowest card sat at y=2970, and `.note-board` is `position: absolute; inset: 0; overflow: hidden` with `document.scrollHeight` equal to the viewport height. No scroll, no pan, no zoom. Organize itself is what pushes cards off the wall, and you cannot drag back a card you cannot see.
- **Blocks:** R20–R22 all assume a wall that holds the cards. R22 ("read the wall") is impossible in the most literal sense at 30% visibility. P14 cannot even be honestly mocked — 13 beats in a row is 2,860px wide, so a spine does not fit on a laptop screen.
- **Notes:** The **viewport is not board data.** Pan and zoom are per-viewer, per-device state and must stay out of the kernel's `BoardState`, or they will end up in the project file and later in Postgres, which D9 says is for user data. Two writers on one board (open question 5) should not share a scroll position.
- **Cost note:** The work is not the transform, it is that every pointer gesture has to convert screen coordinates to board coordinates — card drag, lasso, arrow draw, group drag. That set only grows, so this is cheaper now than after the method features land. **Confirmed in the build:** the transform was an afternoon; the coordinate conversion was the whole job.
- **As built:** the same 53-card board now fits 53 of 53 with nothing stranded. Zoom 15%–250% (D19), viewport never persisted (D18), and drag-on-empty-canvas still lassos rather than pans.

### R25 — A card has a length

- **Status:** built
- **Date:** 2026-09-12
- **Statement:** A card carries an **estimated length** — how much screen time it will take — and the board carries a **target length**. The wall can then say how long the story runs and where the runtime is going.
- **Why:** Step 4 of the method is "look for a **sagging** Act 2." Sagging is a claim about **proportion**: too much runtime between two turns. Today a card is a card, so forty of them say nothing about pages and the board physically cannot answer the first question the method asks. This is the missing ingredient, and it is cheaper than characters (P15) or typed arrows (P16).
- **Unit:** eighths of a page (D23) — what a production breakdown uses, and what Final Draft's Outline Editor already measures in. Today's estimate and tomorrow's measured page (D22) share one unit.
- **What it unlocks:** the distance between consecutive beats, in pages. That is the sag detector, and it needs **no act model** — beats (R20) are the turns and the wall gives the order. "Twenty-two pages between beat 4 and beat 5, four pages between beat 7 and beat 8" is a real reading of a real wall.
- **Notes:** Proportion is robust to a wrong default in a way that a runtime total is not: if every card is one page, proportion is still card distribution, which is a signal writers already eyeball. The estimate sharpens as the outliers get sized.

Initials failed on a legend problem (Maya and Mark are both M) — the thing R16 refused for colour. ### R30 — Typed arrows: a setup and its payoff

- **Status:** **built** 2026-09-12 (P16)
- **Date:** 2026-09-12

### R33 — Undo

- **Status:** **built** 2026-09-13
- **Date:** 2026-09-13
- **Statement:** Any change to the board can be taken back, and taken back again, **whichever door made it** — a drag, a typed line, a tool call from an agent. An agent can also take back its own last change, but never over something a person has done since.
- **Why:** There was none, for people or for agents, and the two newest verbs (`new_board`, `remove_character`) are the most destructive yet. An agent-driven app needs undo more than a hand-driven one: an agent that misreads a wall can rearrange forty cards in a second, and the writer's only recourse was Open project from a file they may not have saved.
- **As built:**
  - **In the store, not the kernel.** The kernel stays a pure reducer. The browser store keeps a history of earlier states (`src/board/history.ts`, pure and tested). What one step is: a **drag** is one step, however many moves it sent; **typing** a headline, a change line, the logline, a group or character name coalesces into one step per line; every other command is a step; and a **change that arrived through the bridge** — an agent's tool call — is a step too, so the person can take back what the agent did. The echo of the wall's own write records nothing.
  - **On the wall:** ⌘Z and ⇧⌘Z (Ctrl on other platforms; ⌘Y also redoes), except inside a field, where the browser's own undo of the text keeps working. Undo and Redo in the general bar's strip and tall layers, greyed when there is nothing to do. Undo pushes the restored board to the bridge, so an agent watching sees it.
  - **For the agent:** an `undo` tool that walks back **this server's own** changes, newest first, and **refuses if the board has changed since** — a person moved on, or another agent did — so it never tramples work. It says what it undid and how many more it can. It cannot undo the person's drag; only the person can, from the wall.
  - **Not persisted.** History lives for the page session and is per viewer, like the viewport (D18). A reload starts it fresh; Save project remains the durable record.
- **Found on the way, in the store:** the bridge echoes every write back over the event stream, and an undo pressed right after a drop could see the drop's echo arrive *after* the undo, mistake it for someone else's change, and re-apply the drag. One end-to-end run in three hit it. The store now remembers the bodies of its writes in flight and ignores their echoes. Undo is only as trustworthy as that.
- **Found on the way, in the kernel:** two warts, both fixed with tests. `settle_note` (the drop at the end of a drag) reported a change even when nothing changed, which would have made every drop an empty undo step. And its margin was 80px, so **dropping the first card of a row-group in place ejected it from the group** — the card's centre sat a card-width from the others' bounds. The margin is now a card width plus a gap. R14's "drag a card out to leave" now means out, not touched.
- **One tool call, one step (2026-09-14, found in an app review):** `create_note` with `characters` committed three times — the card, each new person, the cast — and each write was a frame on the bridge, so ⌘Z on the wall took the cast off the agent's new card and left the card, and the server's own `undo` needed three calls. The server now has `commitAll`: read once, apply every command through the kernel against the running state, write once. Used by `create_note` with a cast, `set_plant` with `later`, `move_scene` (which had one trail entry but a dozen frames on the wall), and both imports. Two more things had to move for the wall's one step to hold the person too: the server now writes the **board frame before the project frame** on the bridge and file doors (the account door keeps the project first, because its live path composes a board's cast against the project row), and the store takes a **bridge board frame's roster as the exact roster** rather than composing the project's over it — a frame from another door is a kernel command's result (R51), and composing the project's roster first meant the recorded step already held the new person. Tested against the file, against a fake bridge that counts frames, and end to end: one ⌘Z on the wall takes back the card, its cast and the person on both channels of the bridge.
- **Notes:** The one thing undo cannot see is a change made by the MCP server *to the file* while the app is closed — there is no wall to undo it from until the app opens, and by then it is simply the board. That is the file door's nature, and `new_board` warns the agent to ask first for that reason.

### R44 — A test account, and a way to take it away

- **Status:** **built** 2026-09-13 (Robert's need, stated while planning the blind runs; plumbing, so no mockup — the question was asked and answered in the plan)
- **Date:** 2026-09-13
- **Statement:** An account can be marked a **test account**: a throwaway a blind run works, which a script may wipe when the round is over. Wiping has two depths — **empty**, which takes the account's projects and leaves the account so the next round signs in with the same address, and **delete**, which takes the account too. Nothing else in PlotCoder knows the mark exists.
- **Why:** The blind runs (`blind-runs/`) are becoming a practice, and each one leaves a wall, a project and possibly files behind on a real Supabase project. Without a way to clear them, either the rounds pollute each other — an agent calling `list_projects` reads five rounds of someone else's leftovers, which is friction the round did not mean to measure — or they are cleared by hand, which is where a real writer's work eventually gets deleted by a typed address.
- **What was already true, and is the reason this is small:** every table cascades off `auth.users` — `writers.user_id`, `projects.owner`, `members.user_id`, `boards` and `assets` through their project. Removing the account removes the rows, in one statement, with no code. **Storage cascades nothing**: objects live at `<project id>/<kind>/<file>` and survive their project, orphaned and unreachable because the policy checks membership of a project that no longer exists. That leak is the whole of what had to be written.
- **As built:**
  - **The flag:** `test boolean not null default false` on `writers` (`supabase/migrations/…_test_accounts.sql`). Default false, so an account is a writer's until someone deliberately says otherwise. **It is not a kind of account** — no client reads it, nothing in the app behaves differently. It is permission for one destructive script, and that is all it is.
  - **The rail is a pure function.** `scripts/wipe-plan.mjs` decides what may go, with nothing that talks to the network, the way `src/board/sync.js` holds the mirror's rules: it refuses an unknown address, refuses an account without the mark by name, and takes only what the account **owns** — a project shared *with* a test account belongs to whoever made it and survives, along with every file under it. Ten tests.
  - **The script:** `scripts/wipe-test-account.mjs`, with `--mark` / `--unmark` to set the flag, `--empty` or `--delete` for the depth. It prints the plan — every project named, every file counted, what survives, and whether the address will have to be claimed again — and **changes nothing without `--yes`**, then asks for the address typed back when a terminal is listening. Files are removed **before** the rows, while the membership the storage policies read still exists.
  - **The key is not in the repo.** `SUPABASE_SERVICE_ROLE_KEY` comes from the environment; the script says so plainly and stops when it is absent. D27's rule holds: the URL and the publishable key ship, the service role never does.
- **What a round leaves behind (Robert's question, 2026-09-17: are whole reports signal or noise?):** measured, the reports were the cheap part — two of them held 28 KB of unique content, while the rounds' paragraphs in this file held 34 KB restating them and two prompts held 31 KB carrying a third copy of one treatment. **Keep every report, whole and unedited**, since it is the only record not written by whoever did the fixing, and its last three sections — what the on-ramp left the agent to work out, what they never found a way to do, what they were never sure had landed — outlast any one fix; each head says which version it is a snapshot of, so a stale log is never read as current behaviour. **A round's paragraph here says what was decided and why** and points at the report for the rest; rounds thirteen and fourteen were cut back on that rule. **One treatment, one file**, and only a prompt that must paste without editing keeps a copy. **`blind-runs/README.md` carries the recurrence table**: the ten requirements that exist because a finding came back, and the two that came back and were deliberately not built — a finding returning is a reason to decide, not a reason to build. If the reports ever become a burden, rounds one to twelve have none and have not been missed, so the last two or three are what earn their place.
- **Deliberately not built:** an MCP tool, and a button in the app. **Not a tool** because the blind-run agent is exactly what the rail protects the writer's work from, and handing it the wipe undoes the point; R26's "a feature without a tool is unfinished" is about a writer's activities with Final Draft, and this is operations, not screenwriting. **Not a button** because it would ship a destructive control to every writer so that one test account could be reset, and it would need a test-account concept inside the product to hang off. The script earns nothing less safely.
- **Notes:** For a wall-only round the bucket stays empty, so deleting the user in the Supabase dashboard is already a complete wipe; this earns its keep the first time a round calls `add_picture` or `add_take`. **Between rounds, prefer `--empty`:** deleting the account means claiming it again, which changes the credentials in the round's prompt and quietly turns every round into a test of `claim_account` instead of the door it meant to test.

## Technical context (for implementers)

- Repo: `https://github.com/plot-coder/plotcoder.github.io`
- Custom domain: `plotcoder.com` (www CNAME to `plot-coder.github.io`)
- Cloudflare zone for Atlas/Robert account; nameservers `clay.ns.cloudflare.com`, `nelci.ns.cloudflare.com`
- App shell is a Vite + React + TypeScript client (proposed stack, now in use for the canvas and general bar)
- GitHub Pages no longer serves the repo root. `.github/workflows/deploy.yml` runs on every push to `main`, installs with `npm ci`, runs `npm test`, builds, and publishes `dist/` through the Pages Actions deploy (the Pages `build_type` is `workflow`, not `legacy`). The custom domain lives in `public/CNAME`, which Vite copies into `dist/`; there is deliberately no `CNAME` at the repo root any more, so there is one source of truth. A failing test blocks the deploy.
- Board state flows through one kernel: `src/board/reducer.js` (plain ESM + `reducer.d.ts` so it runs in the browser and in Node). `src/board/store.ts` is the browser store (localStorage + dev bridge + `window.plotcoder`). The Vite dev bridge (`vite.config.ts`) serves `/__plotcoder/board` and `/__plotcoder/events` and mirrors `.plotcoder/board.json` (gitignored) on localhost only — it never ships to Pages. The MCP server is `scripts/plotcoder-mcp.mjs` (run by `node`; wired in `.cursor/mcp.json` for Cursor and `.mcp.json` for Claude Code); it applies the same kernel and writes the live bridge when the app is open, or the file when it is closed. It needs `npm ci` first — the MCP SDK and `zod` are dev dependencies. The one skill is `.cursor/skills/plotcoder-board/SKILL.md`; `.claude/skills/plotcoder-board` is a symlink to it. `.claude/launch.json` lets the Claude desktop app start the dev server on port 5173. `README.md` is the front door for people; `CLAUDE.md` is the front door for agents.

- **Adding a field to a card** (first done for rank, R20). Same shape as the board-level case below: `normalizeState` fills it in for cards written before it existed, and the default must be the value that claims nothing. `countRanks` lives in the kernel so the general bar and the MCP summary count the same way rather than each rolling their own.
- **Adding a board-level field** (first done for the logline, R19). `BoardState` is `{ logline, targetEighths, notes, groups, arrows }` — the logline came with R19 and the target with R25. The pattern to follow: leave `isBoardState` alone so nothing that used to load stops loading, and repair shape in `normalizeState`, which every load boundary calls — `loadLocal` in `src/board/store.ts`, the bridge adopt path, and both read paths in the MCP server. The browser mirrors the field to its own key (`plotcoder.logline`, `plotcoder.target`), matching the existing one-key-per-list layout.
- **The account mirror (R4, R39–R41)** is `src/board/account.ts`: a thin network layer over `src/board/sync.js` (pure, tested — meeting the account, push outcomes, open outcomes, the conflict rule). The client is `src/supabase.ts`, made on first use so tests never touch it; `VITE_SUPABASE_URL` and `VITE_SUPABASE_KEY` in a `.env.local` point at another project. Auth session and sync bookkeeping live under `sb-plotcoder-*` keys, outside the `plotcoder.` prefix, so Save/Open never carry them. The store grew `boardState`, `replaceBoard` (an undo step on the open board), `adoptProject` and `isSeedProject` for the mirror. Tables are `names`, `projects`, `members` and `boards` on PlotCoder's own project (`kmpahjsggbleygsnuwug`), RLS by membership, with `name_taken`, `my_name`, `my_projects`, `project_people`, `share_project` and `unshare_project` as functions and the `account` edge function for claiming and renaming; the migration is `names_projects_members_boards`. Realtime is on `boards`, `projects` and `members`. The password is hashed on the device (`hashPassword`) with the name as salt, so changing the name re-sets the password hash. The migration SQL and the function's source are kept under `supabase/` in the repo; they were applied through the connector, so the live project is already migrated.
- **Project-level data** lives on the project record (`src/board/project.js`, mirrored to `plotcoder.project` and to the bridge's `/__plotcoder/project`), which is where the premise went in R35. Reminders still keep their own `plotcoder.*` key with a small store (`src/reminderStore.ts`); Save/Open sweeps every `plotcoder.*` key either way.
- `src/EditableText.tsx` is the one caret-safe editable line, used by both the cards and the logline strip. The words are uncontrolled — React never renders them as children — so it cannot rewrite text out from under the caret mid-keystroke; the value is pushed in only while the field is unfocused. Use it for any new tap-the-words-to-type field (D11) rather than writing another `contentEditable`.
- **Structures (R38)** are data in `src/board/templates.js`, applied by the kernel's `apply_template` command so the wall, `window.plotcoder` and the MCP server lay out the same cards; `src/StructureSheet.tsx` is the picker. Add a structure by adding an entry with beats `{ name, prompt, at }`; the sheet, the tool's description and the skill's list follow (the skill's list is by hand).
- **Pagination (R23 c)** is `src/board/paginate.js`, pure: `parseScene` → `layoutScene` → `paginateBlocks`; `sceneLineCount` feeds `measuredEighths` in the kernel so every count agrees; `src/pagesLayout.ts` turns a board into the paginator's input in reading order; `src/board/fdx.js` reads and writes Final Draft with a small tag reader that runs in Node and the browser alike. Print is the browser's, over the `@media print` rules in `styles.css`.
- **Pages (R23 b)** are `text` on the card and nothing else: `noteEighths` in the kernel is the only reading of a card's length (measured when there is text, the estimate otherwise) — never read `lengthEighths` directly for a total or a position. `src/board/fountain.js` holds Fountain out and in; `src/PagesPanel.tsx` is the panel, `src/fountainFile.ts` the file doors. A `.fountain` dropped on Open project merges by heading and order and never deletes.
- **When a scene happens (R55)** is `when` on the note, beside `location`, cleaned like it; `sceneHeading` in `fountain.js` prints it after the place and `splitHeading` takes it apart on the way in. **Story order (R56)** is `storyOrder` in `readWall.js`, the only order any reading, numbering or page uses; `organize.js`'s `arrowOrder` delegates to it.
- **A place on a card (R37)** is `location` on the note and `src/PlaceLine.tsx` on the card (the cast line's shape with one value); `boardPlaces` in the kernel is the only reading of places, so the lens, completion and any report agree. The lens's place focus is separate state in `App.tsx` from the cast focus, and yields to it.
- **The person's page (R36)** is fields on the character record — `CHARACTER_FIELDS` in the kernel, filled by `normalizeState` — and a page mode of `src/CastLens.tsx` (`pageId` state; `scenesOf` reads the person's scenes off `readWall`'s order). Add a line to a page by adding its name to `CHARACTER_FIELDS`, a prompt to `PAGE_LINES` in the lens, and an optional string to the `update_character` tool's schema; the migration and `list_board` follow.
- **The cast (R29)** is the fourth board migration and the model for the next: a list on `BoardState` (`characters`) and ids on the card (`characterIds`), both repaired in `normalizeState`. Name handling is in `src/castNames.ts` (pure, tested): typed names → roster ids, ids → "Maya, Tom", completions for a fragment. The card's line is `src/CastLine.tsx` (an `<input>` while editing, not a third `contentEditable`, because completion needs a controlled value); the panel is `src/CastLens.tsx`; the app resolves typed names and adds strangers in `castNames` in `App.tsx`. The browser mirrors the roster to `plotcoder.characters`.
- **The project (R35)** is `src/board/project.js` (plain ESM + `project.d.ts`): the record and its pure operations. The store (`src/board/store.ts`) owns the record and the open board's state, keeps one `plotcoder.board.<id>` per board, migrates the pre-R35 keys, and speaks two bridge channels — the board's, now carrying `boardId`, and the project's. The MCP server reads the project from the bridge or `.plotcoder/project.json`, and synthesizes a one-board project around a bare `board.json`. `src/ProjectCrumb.tsx` is the crumb and panel.
- **Organize (R34)** is `src/board/organize.js` (plain ESM + `organize.d.ts`, like the kernel): `arrowOrder` and `organizePoses`. `src/organizeLayout.ts` keeps only Scatter's snapshot helpers now.
- **Undo (R33)** is `src/board/history.ts` (pure: a stack with gesture and coalescing rules, tested) owned by the browser store, which records a step on every changed dispatch, on `commit` for a drag, and on adopting a bridge frame that differs from what it holds. `boardStore.undo()` / `redo()` restore a state and push it to the bridge; `getHistory()` is a stable snapshot for React. The MCP server keeps its own trail of `{ before, after }` per commit and its `undo` tool refuses when the board no longer matches `after`.
- **The Story Map (R32)** is `src/storyMapLayout.ts` (pure: positions from the wall's reading order and lengths, label placement, page ticks; tested) drawn by `src/StoryMap.tsx` as a fixed strip. The layout module is named for what it does rather than `storyMap.ts` because a Mac filesystem cannot tell that apart from `StoryMap.tsx`. `centerOn` in `viewport.ts` is the jump. The strip's open state lives in `plotcoder.storyMap`, per viewer.
- **The fold (R31)** is the sixth migration: `plants` on a card, repaired to `false`. The dog-ear is `.note__fold` at the card's top-left, drawn with a gradient flap and a canvas-coloured "cut" rather than a clip-path, so nothing that hangs off the card is clipped. On a beat card it rides up over the top bar.
- **Arrow kinds (R30)** are the fifth migration: `kind` on an arrow, repaired to `follows` in `normalizeState`. The wall draws a setup dashed via `.note-arrow--setup`; the chips at a selected arrow's middle are `.arrow-chips`. Shift while drawing sets the kind at drop.
- Read the wall lives in `src/board/readWall.js` (plain ESM + `readWall.d.ts`, like the reducer) so the Reminders modal and the MCP server read the same wall the same way. `readWall(state)` returns `{ order, beats, runs, findings }`; `describeRuns` turns the runs into the lines both doors print. It is pure: add a check there, test it in `readWall.test.ts`, and both doors get it. Findings are questions with ids, never commands — nothing in it dispatches.
- Pan and zoom live in `src/viewport.ts` — pure functions over a `{ x, y, scale }` view, with no React and no DOM. `NoteBoard` renders one `.board-layer` carrying `translate(x, y) scale(s)`, and every gesture runs its screen coordinates through `toBoard` before touching a card. Scroll and drag pan in **opposite** directions for the same delta, so both signs are pinned in `panByScroll` / `panByDrag` rather than left in an event handler where they are trivially easy to swap.
- Tests run on Vitest: `npm test` (single pass) or `npm run test:watch`. They cover the DOM-free half only — the kernel (`src/board/reducer.test.ts`), the pure helpers (`src/arrowGeometry.test.ts`, `src/organizeLayout.test.ts`, `src/projectStore.test.ts`, `src/viewport.test.ts`), and the MCP server (`scripts/plotcoder-mcp.test.mjs`, which spawns it against a temp board file and a fake dev bridge). No browser, no jsdom. Config is `vitest.config.ts`; `tsc -b` typechecks the `.ts` tests and Vite leaves them out of the bundle.
- End-to-end tests run on Playwright: `npm run test:e2e`. Config is `playwright.config.mjs`; specs and helpers are plain ESM in `e2e/` (like the MCP tests) so they run on any Node 20 without a TypeScript loader — the machine's default Node was 20.0.0, which cannot load a `.ts` config. The config starts its own Vite on port 5174 with `PLOTCODER_BOARD_FILE` pointed at a temp directory, so a run never touches the writer's `.plotcoder/board.json` or an open dev server on 5173; the MCP server it spawns gets `PLOTCODER_ROOT` and `PLOTCODER_BRIDGE_URL` for the same directory and port. The bridge is reset to the seed board before each spec, so specs run one at a time. Seven specs — one per door, one for the Story Map's jump and hide, one for undo across doors, and one for the project (add a board, switch, find the first intact, switch again from the agent's door); add one only when a new door or a bug in an existing one earns it. Chromium needs `npx playwright install chromium` once locally; the workflow installs it with `--with-deps`.

When hosting no longer fits Pages, record the change here.
